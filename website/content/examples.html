Examples

Each example is a statement, the view Definograph drew for it, and how to read that view: what it shows and what it leaves out.

The views are recorded output. The statements are entries in Definograph’s Statement menu; Lean 4.28.0 reads them with Definograph’s pinned copy of Mathlib. To draw them yourself, you need Definograph running on your own computer (see Try it yourself); then choose the statement from that menu.

Which choice may depend on which

In ∀ x : ℝ, ∃ y : ℝ, x < y, may the choice of y use the value of x?

{{view:depends-choices}}
What it shows
The two binders in reading order: x is an arbitrary choice at step 1, y a candidate witness at step 2. Under y, May depend on lists x, so y may be chosen differently for each x.
What it leaves out
The condition x < y, and any value for y. The view does not find or check a witness and does not say whether the statement is true. (It is true: take y = x + 1.)

A choice fixed before the others

With the quantifiers swapped, ∃ y : ℝ, ∀ x : ℝ, x < y, what may y depend on?

{{view:fixed-choices}}
What it shows
y now comes first and is chosen without earlier values, so later choices cannot change it. x lists y under Earlier choices in this scope. One y would have to work for every x.
What it leaves out
The condition, and the fact that this statement is false: no real number is larger than every real number, itself included. The view has the same kinds of steps for the true statement above and this false one.

The outline of a longer statement

In an ε–δ statement, which parts are assumed, which are required, and under which assumptions?

{{view:continuity-overview}}
What it shows
The statement as nested entries: for every ε, given 0 < ε, there is a δ with all of its conditions: 0 < δ, and for every x, given |x| < δ, then |x · x| < ε. Each assumption is written before what depends on it.
What it leaves out
The figures of the individual steps, and any numerical example. The outline comes from the statement as Lean has read it; it is not a proof and does not say whether the statement is true.

Relations and the roles of their objects

In ∀ (A B : Set ℝ) (x : ℝ), A ⊆ B → x ∈ A → x ∈ B, which relations are assumed, and which one is required?

{{view:sets-connections}}
What it shows
Three cards. A ⊆ B is a set inclusion with A as subset and B as superset; x ∈ A and x ∈ B are memberships with x as element. The tags say where each relation sits: the inclusion is the premise of an implication, x ∈ A is under one assumption, and the conclusion x ∈ B is under two.
What it leaves out
Whether any relation holds. A relation drawn under an assumption is not a claim that it holds, and the positions of the cards carry no meaning.

Every object and relation at once

In the same statement, ∀ (A B : Set ℝ) (x : ℝ), A ⊆ B → x ∈ A → x ∈ B, which objects does each relation use, and which objects do the relations share?

{{view:sets-structure}}
What it shows
Nine objects and three relations. The inclusion uses A as subset and B as superset; each membership uses x as element and A or B as set. So A, B and x each connect to two relations.
What it leaves out
Which relation is assumed. The context tags under the map say that relations occur as premises and under assumptions, but not which tag belongs to which relation; the Relationships view above shows that. Position, distance and the curves of the connectors carry no meaning. Some objects are Definograph’s own rather than the statement’s: the name a given to each hypothesis, and x.cauchy, a field of the structure of ℝ. The propositions appear under Lean’s internal names: HasSubset.Subset(A, B) is A ⊆ B, and Membership.mem(A, x) is x ∈ A.

Trace one object through a statement

In ∀ (A B C : Type) (f : A → B) (g : B → C) (h : A → C) (x : A), g (f x) = h x, which relations does x take part in?

{{view:paths-trace-x}}
What it shows
The Structure view with x selected, as you would select it in the app. The connectors of x are drawn heavier, the others are muted, and the relations that use x are marked. Both sides of the equation start from x: one through f and then g, the other through h.
What it leaves out
Anything about x beyond the relations it appears in. There are no concrete functions or coordinates, and the equation is what the statement claims, not something Definograph checks.

One object throughout the reading

Where does the same x appear in the reading of g (f x) = h x?

{{capture:paths-identity-trace}}
What it shows
At step 1, with x selected, a faint dashed line, the identity thread, joins the eight places where the same x appears: its entry and its small x : A box at this step, the same two in the full visual statement, the start of both compared routes, and the inputs of f and h.
What it leaves out
Any meaning in the line itself. Its route means nothing: it only links the places, and it is not a path or a movement. The thread is drawn from the positions of the page’s elements, so it is recorded as a screenshot at its own size.

Membership regions of a compound set

In ∀ (α : Type) (A B C : Set α) (x : α), x ∈ (A ∪ B) ∩ Cᶜ → x ∈ (A \ C) ∪ (B \ C), what does the assumption allow for x?

{{view:set-algebra-given}}
What it shows
The type α as a box with circles for A, B and C. The highlighted regions are the membership combinations the assumption allows: in A only, in B only, or in both, each outside C. The element must lie somewhere in the highlighted part.
What it leaves out
Sizes, elements and whether any region is inhabited: the regions encode membership combinations only. This condition is the assumption of an implication, not a claim that it holds.

What a coloring requires on each edge

In ∀ (V C : Type) (G : SimpleGraph V) (c : G.Coloring C) (u v : V), G.Adj u v → c u ≠ c v, what does the coloring c promise?

{{view:coloring-follow}}
What it shows
The step applies c to u, under the assumption that u and v are adjacent. The figure shows the rule a proper coloring carries: if two endpoints are adjacent, their labels differ, for every edge. The color type C stays symbolic.
What it leaves out
A graph. The endpoint slots stand for arbitrary inputs to the rule; they do not pick vertices, assert that an edge exists, or fix the size or shape of the graph. No coloring and no number of colors is chosen.

A ball as a distance condition

In the statement below, what does P ∈ Metric.ball c ε require of P?

{{view:epsilon-ball}}
What it shows
The membership read as dist(P, c) < ε, drawn as an open disc with center c, radius ε and a named point P. The figure notes that it uses the local assumption 0 < ε and that the boundary is excluded.
What it leaves out
Coordinates and sizes: the positions are schematic, and named points may coincide. Here the membership is an assumption of the implication, not a claim that P lies in the ball. Numerical samples belong to a different view.

One numerical sample

What does the same statement look like for particular values?

{{view:epsilon-sample}}
What it shows
One sample from Explore a sample: ε = 1, the center c at the origin and the point P at the center, so here P lies in the ball. The disc is the open ball in the Euclidean metric, boundary excluded.
What it leaves out
The statement itself. A sample is an illustration under chosen values, not a proof, and other values can make the condition fail. In the app the point can be moved; in this recording nothing moves.

A map that is inverse only on a region

In ∀ (A B : Type) (e : PartialEquiv A B) (x : A), x ∈ e.source → e.symm (e x) = x, why is the assumption x ∈ e.source needed?

{{view:restricted-inverse-return}}
What it shows
The two carriers with the regions e.source and e.target, each marked as possibly empty; the maps e and its inverse between them; and the two round trips that return to their start, for every element of each region. The step follows x through e and back.
What it leaves out
Geometry: the carriers are abstract containers without shape, size or dimension. The inverse laws hold on the designated regions only. Applying e to x does not by itself put x in the source region; the statement assumes it.

Inside a structure

In the same statement, what does e : PartialEquiv A B contain?

{{view:restricted-inverse-fields}}
What it shows
The fields of e with their declared types: the maps toFun and invFun, the sets source and target, and the laws that link them, read in declaration order. The fields belong to this e, inside the statement’s quantifiers.
What it leaves out
One further law: the view says that a field is not shown, because reading it would exceed Definograph’s size limit for this part. The laws are requirements of the structure, not extra assumptions and not proofs.

Opening a definition

In ∀ (α β : Type) (f : α → β), Function.Injective f → ∀ x y : α, f x = f y → x = y, what does the assumption Function.Injective f say?

{{view:maps-expanded-overview}}
What it shows
The whole statement after Function.Injective f has been opened one step. The assumption now reads: for every a₁, a₂, given f(a₁) equals f(a₂), then a₁ equals a₂. Definograph opened it with a definition step that Lean checked for definitional equality.
What it leaves out
A proof that f is injective: the opened assumption is still an assumption. The figures of the individual steps.

What Definograph could not interpret

In ∀ (P : ℝ × ℝ) (ε : ℝ), P ∈ Metric.ball 0 ε → Nat.Prime 17, which parts does Definograph interpret?

{{view:partial-coverage}}
What it shows
Definograph’s Interpretation coverage: the ball condition is interpreted (sets and membership, metric regions), Nat.Prime is kept as structure only, and its definition is available to look inside.
What it leaves out
Understanding: the report counts the vocabulary a statement uses. It does not measure understanding or establish the statement.

Lean files

These downloadable files accompany the tutorial and the reference. They use Lean 4.28.0 with its standard implicit Init import; none needs Mathlib. To check one, run lean FileName.lean in its directory. The example notes give the expected result of checking each file used in the tutorial; the table below says what each file contains.

Downloadable Lean files
File What it contains
QuantifierForallExists.lean The proposition ∀ x : Nat, ∃ y : Nat, y = x. It supplies no proof.
QuantifierExistsForall.lean The same proposition with the quantifiers swapped. It supplies no proof.
QuantifierProofs.lean A proof of the first proposition and a refutation of the second, shown below.
Scope.lean Both quantifier orders, the same statement with renamed variables, and a statement that allows a constant choice.
RotorLaw.lean A record with a law field, used in the reference. It has an intentionally unused parameter.
RotorExamples.lean Two records of that kind, one with natural-number carrier and one with an empty carrier, and the law applied to an input.
Evidence.lean A proof from a local hypothesis beside an unfinished proof, with their axiom reports.
ReturnMap.lean A record of two maps and a return law, a counterexample to its converse, and a proof of injectivity.
RecordedAxiom.lean A deliberately unfinished proof and its sorryAx dependency, explained under checking evidence. Checking it produces a warning that the declaration uses sorry.

Proof supplement: prove one order, refute the other

This supplement contains two proofs, separate from the source files that form the propositions. each_has_equal chooses x as the witness for each x. no_one_equals_all derives the impossible equality 0 = 1 from the claim that one number equals every number.

Both theorems have been independently checked with Lean 4.28.0 and have no axiom dependencies. The difference between forming a proposition and proving it is the subject of {{lesson:06-checking-evidence.md}}.
